# 代码评审规范与检查清单 (Code Review Guidelines)

代码评审（Code Review）是保障代码健康度、传递工程知识与防止缺陷流入主干的核心环节。

## 1. 评审者与作者的基本约定

### 1.1 作者职责 (Author)
- **提交前自检**: 提交 PR 前必须在本地运行代码格式化、静态检查与所有单元测试。
- **原子化提交**: 保持单个 PR 规模适中（建议修改行数控制在 400 行以内），一个 PR 只聚焦解决一个明确的问题。
- **详尽上下文**: PR 描述中需说明“背景原因”、“关键实现设计”以及“测试验证方式”。
- **欢迎反馈**: 对评审意见保持开放心态，技术讨论对事不对人。

### 1.2 评审者职责 (Reviewer)
- **及时响应**: 原则上工作日内 24 小时内给出第一轮评审意见。
- **建设性反馈**: 提出问题时说明背后的原因，并尽可能给出具体的修改建议或替代方案。
- **区分严重等级**:
  - `[BLOCKER]`: 阻塞性缺陷（安全漏洞、逻辑严重错误、资源泄露、未处理的边界），必须修改方可合并。
  - `[SHOULD]`: 强烈建议（可读性欠佳、架构异味、复杂度超标），作者若不采纳需给出合理解释。
  - `[NIT]`: 细微点或个人建议（拼写、微小命名喜好），不阻塞合并。
  - `[PRAISE]`: 对优秀的架构设计或优雅实现给予积极反馈。

## 2. 跨语言代码评审核心清单

### 2.1 架构与设计
- [ ] 变更是否符合当前模块的职责定位？是否存在越界或不当耦合？
- [ ] 是否存在不必要的抽象、过早优化或过度设计？
- [ ] 公共 API 的命名、入参和返回值是否清晰且符合惯用范式？
- [ ] 是否破坏了既有模块的向后兼容性（ABI/API）？

### 2.2 正确性与边界处理
- [ ] 是否穷举了可能的边界条件（空指针、None、空数组、溢出、负数、超时）？
- [ ] 错误处理分支是否正确释放了已申请的局部资源？
- [ ] 状态机的转移是否完备？是否存在无法跳出的死锁或不可达状态？
- [ ] 并发/多线程/中断场景下共享变量的访问是否有完备的同步保护机制？

### 2.3 性能与资源
- [ ] 是否存在明显的资源泄露路径（未关闭的句柄、内存泄露）？
- [ ] 关键循环体内是否存在不必要的高开销操作（如重复 I/O、无意义的深拷贝、重复正则编译）？
- [ ] 数据结构与算法的选择是否与预期数据量级匹配？

### 2.4 可测试性与文档
- [ ] 新增或修改的代码是否有对应的自动化测试覆盖？
- [ ] 测试是否验证了错误分支？
- [ ] 复杂逻辑或非常规决策是否有解释“Why”的注释？
- [ ] 项目相关 README 或 API 文档是否同步更新？
